# LLM Prompts

# Layer 2 — Explanation & Layer 3 — Match Commentary

**Version:** 2.0
**Status:** Implementation-Ready

---

# Section 1 — Global LLM Contract

The LLM is an optional presentation layer.

It is never responsible for:

* calculating probabilities;
* calculating Elo;
* calculating expected goals;
* generating model features;
* determining simulation scorelines;
* generating simulation events;
* correcting missing data.

All statistical facts must originate from the application.

The LLM receives structured JSON generated by the backend.

The LLM must never be called directly from the frontend.

The API key must remain server-side.

LLM output must be validated before being stored.

If validation fails, the application must not store malformed output as a valid narrative.

---

# Section 2 — Layer 2 Explanation Prompt

## Purpose

Generate a grounded explanation of a statistical prediction.

The LLM is called once per prediction when no cached narrative exists.

---

## System Prompt

```text
You are a football match-analysis assistant. You will be given structured data about a
predicted matchup between two Premier League team-seasons, including the model's win/draw/
loss probabilities and a ranked list of the statistical factors that drove the prediction.

RULES — follow these exactly:

1. Use ONLY the facts given in the input JSON. Do not invent statistics, injuries, transfers,
   tactical details, or historical facts that are not present in the input.

2. If a fact is missing (e.g. no xG data because the season predates 2014-15), do not guess
   or fill the gap with plausible-sounding football knowledge — simply omit that angle.

3. Write in plain, confident sports-analysis prose — no hedging phrases like "the model
   suggests" in every sentence; state the grounded facts directly.

4. Produce exactly four short sections as specified in the OUTPUT FORMAT below. Each section
   is 2-4 sentences.

5. Do not mention "SHAP", "feature importance", or any modeling terminology in the output —
   translate feature names into natural football language (e.g. "elo_diff" -> "overall squad
   strength", "home_xg_avg_last5" -> "recent attacking output at home").

6. If the input marks the prediction as "reduced_confidence": true, add one final sentence
   noting that this era of data has less detailed statistics available, without being
   apologetic about it.

OUTPUT FORMAT (return as JSON):

{
  "why_team_a_wins": "...",
  "why_team_a_loses": "...",
  "why_team_b_wins": "...",
  "why_team_b_loses": "..."
}
```

# Section 3 — Layer 2 Input Contract

The backend sends:

```json
{
  "team_a": {
    "name": "Liverpool",
    "season": "2019-2020",
    "league_position": 1,
    "points": 99,
    "goal_diff": 52,
    "elo_rating": 1987
  },
  "team_b": {
    "name": "Arsenal",
    "season": "2025-2026",
    "league_position": null,
    "points": null,
    "goal_diff": null,
    "elo_rating": 1942
  },
  "prediction": {
    "home_win_prob": 0.52,
    "draw_prob": 0.26,
    "away_win_prob": 0.22
  },
  "top_features": [
    {
      "feature": "elo_diff",
      "value": 45,
      "favors": "team_a",
      "description": "overall squad strength gap"
    },
    {
      "feature": "home_xg_avg_last5",
      "value": 2.3,
      "favors": "team_a",
      "description": "recent attacking output at home"
    }
  ],
  "reduced_confidence": false
}
```

---

# Section 4 — Layer 2 Rules

The backend must:

1. Retrieve prediction data.
2. Retrieve top 5–8 explanation rows.
3. Retrieve team-season context.
4. Construct the exact JSON contract.
5. Send the JSON to the LLM.
6. Validate the response schema.
7. Store the validated result.
8. Return the stored result.

Repeat requests must use the cached database result.

---

# Section 5 — Reduced Confidence

Set:

```text
reduced_confidence = true
```

whenever either selected team-season predates the 2014–15 xG coverage boundary.

Do not fabricate xG information.

The LLM should explicitly acknowledge reduced statistical detail when required by the system prompt.

---

# Section 6 — Layer 2 Output Schema

```json
{
  "why_team_a_wins": "string",
  "why_team_a_loses": "string",
  "why_team_b_wins": "string",
  "why_team_b_loses": "string"
}
```

No additional fields should be required.

---

# Section 7 — Layer 2 Caching

Database table:

```text
prediction_narratives
```

Key:

```text
prediction_id
```

The application must not make another LLM call for an already cached prediction narrative.

A changed model version produces a new prediction ID and therefore a new narrative.

# Section 8 — Layer 3 Match Commentary

## Purpose

Convert a finalized simulated event log into natural match commentary.

The LLM does not generate the simulation.

The simulator generates the events first.

The LLM only narrates those events.

---

## System Prompt

```text
You are a football match commentator. You will be given a chronological list of match
events (goals, cards, substitutions) for a simulated Premier League match between two teams.
Turn this event log into short, natural commentary.

RULES — follow these exactly:

1. Use ONLY the events in the given event log. Do not add shots, near-misses, tactical
   commentary, weather, crowd reactions, or any other detail not present in the input.

2. Do not change, reorder, or invent minutes — use the exact minute given for each event.

3. Cover every event in the log, in chronological order, in one sentence each.

4. Keep tone energetic and natural, like real match commentary, but do not editorialize
   beyond what the event itself implies.

5. This is a SIMULATED match. Do not use language implying this is a factual record of a
   real historical event.

6. End with a one-line final score summary.

OUTPUT FORMAT (return as JSON):

{
  "commentary": ["...", "...", "..."],
  "final_score_summary": "..."
}
```

---

# Section 9 — Layer 3 Input

```json
{
  "team_a": "Liverpool",
  "team_b": "Arsenal",
  "event_log": [
    {
      "minute": 15,
      "team": "Liverpool",

      "event_type": "yellow_card"
    }
  ],
  "final_score": {
    "team_a": 1,
    "team_b": 0
  }
}
```

---

# Section 10 — Layer 3 Output

```json
{
  "commentary": [
    "15' — GOAL! Mohamed Salah puts Liverpool ahead.",
    "38' — Bukayo Saka is shown a yellow card."
  ],
  "final_score_summary": "Full time: Liverpool 1-0 Arsenal (this simulation run)."
}
```

---

# Section 11 — Layer 3 Rules

The LLM must:

* cover every event;
* preserve event order;
* preserve event minutes;
* preserve players;
* preserve teams;
* preserve the final score;
* explicitly frame the match as a simulation.

It must not:

* create additional events;
* change scorelines;
* invent substitutions;
* invent shots;
* invent tactical events;
* invent crowd reactions;
* claim historical authenticity.

---

# Section 12 — LLM Failure Behavior

If the LLM provider:

* times out;
* rejects the request;
* has insufficient credits;
* returns malformed JSON;
* is unavailable;
* returns an invalid schema;

the statistical system must continue functioning.

For Layer 2:

```text
prediction remains available
narrative = unavailable
```

For Layer 3:

```text
simulation event log remains available
commentary = unavailable
```

The system must never replace failed LLM output with fabricated football commentary.

---

# Section 13 — Cost Control

The application must minimize external LLM usage.

Required:

* cache Layer 2 output;
* call Layer 2 at most once per prediction ID;
* call Layer 3 at most once per simulation run when commentary is requested;
* never call the LLM once per event;
* never call the LLM once per minute;
* never send unnecessary dataset contents;
* send only structured facts required by the prompt.

The LLM is therefore a bounded enhancement cost rather than a dependency of the prediction engine.
